From call router to AI that solves the call

How ElevenLabs, Vapi, Retell and Bland build phone agents, what they charge, and how to build SmartCallAI's version in TypeScript on the Vercel AI SDK with no Python backend.

2026-09-25~45 sourcesPrices checked on vendor pagesConfidence: medium-high

TL;DR

  • The pivot: today the AI classifies the caller and hands them to a human. The new version talks to the caller, uses tools to fix the problem (look up an account, reset something, open a ticket), and only transfers to a human when it can't. Your existing agents table becomes the escalation path.
  • Every platform does the same three things: it turns speech into text, runs an LLM with tools, and turns the reply back into speech, all within about a second. Most of the engineering goes into turn-taking and interruptions.
  • Market price is about $0.08–0.15 per minute all-in. ElevenLabs charges $0.08/min plus LLM. Vapi charges $0.05/min plus every component. Retell's total is $0.07–0.31/min. Bland charges a flat $0.12–0.14/min.
  • The AI SDK is v7 (ai@7.0.114). It is a good fit for the "brain": streamText, tool(), ToolLoopAgent, structured output, and stable transcribe/generateSpeech. It does not handle phone audio. Pair it with a telephony layer.
  • Recommendation: use Twilio ConversationRelay (Twilio handles speech in and out plus interruptions) and connect it to our own AI SDK agent. It's all TypeScript, costs about $0.09–0.10/min, and we own the logic. The only extra infrastructure is one small WebSocket service.

02How a phone AI agent works

Two architectures. Almost every platform uses the first.

Cascaded pipeline: speech-to-text → LLM → text-to-speech

Caller→ Phone network (Twilio)→ Speech-to-text→ LLM + tools (our code)→ Text-to-speech→ Caller hears reply

Each stage streams, so the voice starts playing before the LLM has finished its sentence. This is the flexible option: you pick any LLM, any voice, and your own tools. This is where the AI SDK fits.

Speech-to-speech: one model hears and speaks

OpenAI's gpt-realtime and Gemini Live take audio in and produce audio out directly. Latency and intonation are better, but it costs more (roughly $0.18–0.21/min in one benchmark, unverified), you have less control, and the AI SDK support for it is still experimental.

The latency budget

A reply has to start about a second after the caller stops talking, or the call feels broken. Here is Twilio's published target for a cascaded agent:

Speech-to-text
350ms
LLM first token
375ms
Voice first audio
100ms
Total turn gap
1,115ms

Blogs cite "under 800ms feels natural". To get there, use a fast, small LLM, keep the prompt short (fetch knowledge with a tool instead of pasting it in), and host the server close to Twilio's US-East edge.

The hard parts (what the platforms really sell)

  • End-of-turn detection: is a pause the caller thinking, or finished? Fixed silence timers (~500ms) cut people off. Model-based detection (OpenAI semantic_vad, LiveKit's turn detector) is better.
  • Barge-in: when the caller talks over the AI, stop the audio immediately and stop the LLM too. With ConversationRelay, Twilio sends us an interrupt message and we abort the stream.
  • Tools that actually resolve things: account lookup, resets, refunds, tickets, bookings. The model decides when to call them. Our server checks and authorizes every call.
  • Handoff: a cold transfer (end the AI session, dial a human) or a warm transfer (the human joins a conference, and the AI briefs them and leaves).
  • After the call: a transcript, a summary, "was it resolved?" scoring, and pulling structured data out of the conversation. ElevenLabs sends these through post-call webhooks. We can do the same with generateText plus Output.object.

05The Vercel AI SDK (v7) for a voice agent

What it gives us, what changed, and what it doesn't cover.

Current state

  • ai@7.0.114 is latest on npm (released 24 Sep 2026). v5 and v6 still get patches, but most tutorials online are v5/v6 and use old names. v7 needs Node 22+ and is ESM-only.
  • Provider packages: @ai-sdk/openai@4, plus @ai-sdk/anthropic, @ai-sdk/elevenlabs, @ai-sdk/deepgram. Or skip them and use AI Gateway model strings like "openai/…" with no markup on tokens, fallbacks, and budgets.

Hosting on Vercel: the one real constraint

A phone call through ConversationRelay is one WebSocket that lasts the whole call. Vercel Functions can serve WebSockets as of June 2026, but it's a public beta, you need experimental_upgradeWebSocket() in Next.js, and the socket closes when the function hits its max duration: 300s on Hobby, 800s on Pro, and 1,800s (30 min) in the extended beta. When the socket closes, the call drops.

So: prototype on Vercel if you like, but run the call socket as a small, always-on Node service (Fly.io / Railway / Render, US-East). The Next.js app stays on Vercel for the dashboard, APIs and database. Both share the same TypeScript lib/ code.

06Three ways to build it (all TypeScript)

OPTION A

Twilio ConversationRelay + AI SDK

Twilio does speech-to-text (Deepgram), the voice (ElevenLabs by default) and interruptions. It sends us text over a WebSocket, and we stream text back from streamText.

✓ We own the agent · ✓ AI SDK does all the thinking · ✗ Needs one small WebSocket service

≈ $0.085–0.10 / min
OPTION B

ElevenLabs Agents + our AI SDK as "custom LLM"

ElevenLabs runs the phone, voice and turn-taking. It calls our Next.js route, which runs streamText and returns OpenAI-format streaming.

✓ Plain HTTP, runs on Vercel as-is · ✓ Best voices · ✗ Their dashboard, their lock-in · ✗ No official AI SDK example

≈ $0.09–0.13 / min
OPTION C

OpenAI Realtime over SIP

A Twilio SIP trunk connects straight to OpenAI's speech-to-speech model. We accept calls, run tools and transfer through webhooks.

✓ Lowest latency · ✓ No media server · ✗ Barely uses the AI SDK · ✗ Locked to one model

≈ token-based, roughly $0.03–0.10+ / min

07Recommendation

Build this

Option A: Twilio ConversationRelay → our AI SDK agent

It matches what you asked for: the Vercel AI SDK is the brain, with no Python and no platform lock-in. Twilio handles the audio work that is hardest to get right (speech recognition, voices, barge-in), and our TypeScript code handles everything else: the conversation, tools, Supabase, and escalation to the humans we already model.

  • Fallback: if you want the ElevenLabs experience with the least infrastructure, Option B reuses the same AI SDK agent code behind an HTTP route. The agent (instructions + tools) is written once and runs behind either.
  • Keep the web call screen as a test console. It can hit the same agent over text with useChat, which is how we'll test tools without dialing a phone.
  • Model: start with a small, fast model for latency (the repo already uses gpt-4o-mini). Route through AI Gateway so we can swap or add a fallback without code changes.

08Starter code (sketch)

Written against the v7 docs checked today. It's a starting point and has not been run yet. The shapes of Twilio's messages (setup, prompt, interrupt, text, end) come from Twilio's docs.

1. The agent: lib/voice-agent.ts (shared by phone and web)

import { tool } from "ai";
import { z } from "zod";
import { findAvailableAgent } from "@/lib/agents";

export const instructions = `You are SmartCall, a phone support agent.
Speak in short, natural sentences (this is read aloud). Solve the caller's
problem with your tools. Only transfer when you cannot help or they insist.`;

export function makeTools(ctx: { callSid: string; onTransfer: (reason: string, phone: string) => void }) {
  return {
    lookupCustomer: tool({
      description: "Find the caller's account by phone number",
      inputSchema: z.object({ phone: z.string() }),
      execute: async ({ phone }) => ({ /* query Supabase */ }),
    }),
    createTicket: tool({
      description: "Open a support ticket when follow-up is needed",
      inputSchema: z.object({ summary: z.string(), category: z.string() }),
      execute: async (t) => ({ ticketId: "…" }),
    }),
    transferToHuman: tool({
      description: "Hand the caller to a human agent",
      inputSchema: z.object({ category: z.string(), reason: z.string() }),
      execute: async ({ category, reason }) => {
        const agent = await findAvailableAgent(category);   // existing code
        if (!agent) return { queued: true };
        ctx.onTransfer(reason, agent.phone);
        return { transferringTo: agent.name };
      },
    }),
  };
}

2. The call socket: voice-server/index.ts (small Node service)

import { WebSocketServer } from "ws";
import { streamText, isStepCount, type ModelMessage } from "ai";
import { openai } from "@ai-sdk/openai";
import { instructions, makeTools } from "../lib/voice-agent";

const wss = new WebSocketServer({ port: 8080 });   // verify X-Twilio-Signature on upgrade

wss.on("connection", (ws) => {
  const messages: ModelMessage[] = [];
  let callSid = "";
  let abort: AbortController | undefined;

  const send = (m: object) => ws.send(JSON.stringify(m));
  const tools = () => makeTools({
    callSid,
    onTransfer: (reason, phone) =>
      send({ type: "end", handoffData: JSON.stringify({ reasonCode: "live-agent-handoff", reason, phone }) }),
  });

  ws.on("message", async (raw) => {
    const msg = JSON.parse(raw.toString());

    if (msg.type === "setup") callSid = msg.callSid;
    if (msg.type === "interrupt") abort?.abort();          // caller talked over us
    if (msg.type !== "prompt") return;

    messages.push({ role: "user", content: msg.voicePrompt });
    abort = new AbortController();
    const result = streamText({
      model: openai("gpt-4o-mini"),
      instructions,
      messages,
      tools: tools(),
      stopWhen: isStepCount(4),
      abortSignal: abort.signal,
    });

    for await (const token of result.textStream) send({ type: "text", token, last: false });
    send({ type: "text", token: "", last: true });
    messages.push(...(await result.response).messages);
  });
});

3. Answering the phone: app/api/voice/incoming/route.ts (Next.js on Vercel)

// Twilio number → "A call comes in" webhook → this route.
export async function POST() {
  const twiml = `<Response>
  <Connect action="${process.env.APP_URL}/api/voice/handoff">
    <ConversationRelay url="${process.env.VOICE_WS_URL}"
      welcomeGreeting="Hi, this is SmartCall. How can I help?" />
  </Connect>
</Response>`;
  return new Response(twiml, { headers: { "Content-Type": "text/xml" } });
}
// /api/voice/handoff reads HandoffData and returns <Dial>{phone}</Dial> to reach the human.

09Build plan

Each step ends with something you can try.

  1. Agent on the web first

  2. Mock backend tools

  3. Phone number

    Buy a Twilio number ($1.15/mo) and point it at /api/voice/incoming. Run the voice-server locally behind a tunnel (ngrok/cloudflared) and make a real call.

  4. Interruptions + escalation

    Handle interrupt (abort), transferToHuman → end + <Dial>, and mark the human busy using the existing logic.

  5. After-call analytics

    On hang-up, use generateText + Output.object to produce a summary, "resolved?" and a category, then write them to calls. Add a resolution rate and cost per call to the analytics page.

  6. Deploy

    Next.js on Vercel. voice-server on Fly/Railway in US-East. Add rate limits and Twilio signature checks. Test with 10 scripted calls.

10Risks, conflicts and gaps

  • No official AI SDK + Twilio example exists. Twilio's ConversationRelay samples use other SDKs. The glue code above is ours to write and test.
  • Latency is unproven for this stack. Twilio publishes no ConversationRelay latency figures, and vendor claims (Vapi <600ms, Bland <400ms) are their own. Measure it in step 3.
  • Vercel WebSockets are beta and cap call length, which is why the voice server is separate.
  • Prices move. All figures were observed 2026-09-25. Retell's "$0.07/min" floor couldn't be reproduced from its own listed parts, and Bland's figure on third-party blogs (~$0.09) is out of date.
  • Model names in vendor docs (e.g. on Retell's page) were not checked against the model providers. Check the live model list before hard-coding.
  • The hosted Supabase project is currently unreachable (found earlier today), so local development uses the local Supabase stack.
